# Semantic TextNavigator

Локальный прототип для специалиста по закупкам: извлекает условия из TXT, показывает действующие сумму и срок поставки на выбранную дату и позволяет сверить результат с точной цитатой. Шесть учебных TXT находятся в `PO_Vibecoding_Task/` и не изменяются приложением. Компании и условия в них вымышлены. Оригинальное задание работодателя в DOCX не включено в публичный репозиторий и его историю.

## Запуск и зависимости

Нужны современный браузер и Python 3 для статической раздачи файлов. Для автотестов нужен Node.js с встроенным `node:test` (рекомендуется Node.js 22+). Проверено с Node.js 24.17.0 и Python 3.9.6. Устанавливать npm-пакеты, вводить ключи или создавать аккаунты не требуется.

Склонируйте публичный репозиторий (нужен Git), затем запустите сервер. При скачивании ZIP вместо клонирования перейдите в распакованную папку и выполните команду запуска сервера.

```sh
git clone https://github.com/stanyanovsky/semantic-textnavigator.git
cd semantic-textnavigator
python3 -m http.server 8000 --bind 127.0.0.1
```

Откройте [локальное приложение](http://127.0.0.1:8000/). Остановить сервер: `Ctrl+C`. Если порт занят, укажите `8765` вместо `8000` и откройте соответствующий адрес. Открытие `index.html` через `file://` не поддерживается из-за ES-модулей. Python используется только как статический сервер: обработка документов происходит в памяти браузера, загруженный текст не отправляется на сервер.

```sh
node --test tests/core.test.mjs
```

## Пример и ручная проверка

1. Выберите все шесть оригинальных TXT в `PO_Vibecoding_Task/`. Дата проверки по умолчанию — 10.03.2026.
2. Убедитесь, что таблица отвечает на вопросы задания:

   | Вопрос | Ожидаемый ответ на 10.03.2026 |
   | --- | --- |
   | Срок STN-101 | 30.04.2026, источник — подписанное допсоглашение |
   | Сумма STN-102 | 840 000 ₽ |
   | Сумма STN-103 | Нет данных; бюджетный лимит не используется |
   | Поставка раньше 01.04.2026 | STN-102; отдельно показано предложение переноса на 27.03.2026 |

3. Раскройте «Основания и точные цитаты» у суммы или срока, нажмите ссылку файла: откроется полный текст с подсвеченным абзацем. Для изменённого условия указан файл соглашения.
4. Измените дату проверки на 28.02.2026: STN-101 должен показывать 1 200 000 ₽ и 15.04.2026 без повторной загрузки. Верните 10.03.2026.
5. Установите фильтр «Поставка раньше» на 01.04.2026: останется STN-102. Сбросьте фильтр. Проект по STN-101 и письмо по STN-102 не меняют итоговые условия.
6. Для проверки устойчивости используйте копии: измените сумму/срок, добавьте договор того же формата с новым номером и загрузите весь нужный набор повторно. Новый выбор заменяет предыдущий набор, перезагрузка страницы очищает его. Не редактируйте оригиналы.

Контрольные ответы выше служат для проверки и не встроены в бизнес-логику.

## Проверенный результат

- Финальный прогон: **21 тест, 21 успешно**. Покрыты исходники, новые номера/значения, отсутствие сведений, конфликты, дубли, неподписанные изменения, даты подписания и вступления, независимые изменения полей, фильтр, точные источники и регрессия «без изменений».
- Проверены синтаксис обоих JS-модулей и запуск чистого снимка Git без установки пакетов: HTML, CSS и оба модуля возвращают HTTP 200. Проверка выполнялась на существующем окружении с установленными Node.js/Python, а не на новой ОС.
- В браузере в итерации 3 проверены загрузка шести файлов, четыре ответа задания, пересчёт даты, фильтр и переход с раскрытием/подсветкой исходного абзаца. Финальная проверка не повторяла браузерный сценарий.
- Перед публикацией проверено совпадение шести учебных TXT с локальной исходной версией. Публичная история создана отдельно без DOCX работодателя и прежних коммитов с личным email автора. Поиск типичных маркеров секретов в публикуемых текстах совпадений не дал; это не специализированный аудит безопасности.
- По результатам ручной приёмки пользователя подтверждены: загрузка шести исходных TXT; правильные действующие условия STN-101, STN-102 и STN-103; пересчёт при изменении даты; фильтрация по сроку поставки; раскрытие цитат и переходы к подсвеченным абзацам.
- Пользователь также подтвердил обработку копии STN-102 с изменением суммы с 840 000 до 950 000 ₽; добавление STN-104 четвёртой строкой таблицы; обнаружение дубликата основного договора STN-101 с предупреждением. Это результаты ручной приёмки, не браузерной автоматизации.
- Ручная проверка изменения срока в копии документа и остальных предупреждений на нестандартных документах не подтверждена. Обнаружение дубликата не означает проверки всех вариантов конфликтов.

## Краткая продуктовая и техническая записка

### Пользователь, правила и допущения

Специалисту по закупкам нужно быстро проверить сумму и срок и убедиться, что изменение согласовано. Прототип поддерживает UTF-8 TXT, включая BOM и CRLF, с явными номерами договоров, числовыми суммами в рублях, датами `ДД.ММ.ГГГГ` и формулировками общего формата учебных документов.

Связь определяется номером в тексте. Сумма и срок разрешаются независимо: применяются только допсоглашения с подтверждёнными подписями обеих сторон и наступившими датами подписания и вступления в силу. Приоритет — более поздняя дата вступления для конкретного поля; противоречия на одной дате требуют проверки. Письма и проекты не применяются. Неизменённое поле наследуется, явное нераспознанное изменение в поддерживаемом шаблоне блокирует наследование. Подписи распознаются по текстовому статусу, криптографическая подлинность не проверяется.

«Нет данных» означает отсутствие извлечённого значения, «Требует проверки» — распознанную неоднозначность или недостаточное основание. Неопределённые сроки исключаются из фильтра с предупреждением. Неизвестные формулировки могут остаться нераспознанными: это не универсальный юридический анализатор. Приложение не извлекает ставку неустойки; OCR, PDF/DOCX, произвольный чат и сохранение состояния вне MVP. Оно не проверяет полноту комплекта приложений.

### Пять вопросов клиенту

1. Какие форматы, типовые формулировки и виды изменений чаще встречаются в реальных договорах?
2. Как различать договоры с одинаковым номером у разных поставщиков или за разные годы?
3. Как трактовать обратную силу, отмену соглашений и противоречия между приложениями?
4. Кто подтверждает спорные факты и какой след проверки необходимо хранить?
5. Какие роли, ограничения доступа и требования к хранению документов обязательны?

### Две метрики

1. Медианное время ответа закупщика на контрольный вопрос с проверкой цитаты — сравнить с ручным чтением тех же документов.
2. Доля полей с корректными значением, статусом и источником на размеченной выборке — считать для суммы и срока, включая случаи отсутствия и неоднозначности.

Метрики предложены для пилота; пользовательских измерений пока нет.

### Архитектура и три решения

`index.html` и `styles.css` задают интерфейс. `src/app.mjs` читает файлы, хранит набор в памяти и перерисовывает результаты. `src/core.mjs` содержит чистые функции `parseDocument`, `buildContractView` и `filterContracts`. Факт хранит статус, значение и доказательства: имя файла, ID абзаца, точную цитату; абзацы имеют диапазоны символов исходника. `tests/core.test.mjs` использует встроенный `node:test`.

1. Правила вместо LLM: воспроизводимость, отсутствие стоимости и внешних вызовов; компромисс — ограниченный словарь поддерживаемых формулировок.
2. Независимое разрешение полей с доказательствами: можно проверить каждое значение и частичное изменение; компромисс — неоднозначные основания требуют человека.
3. Статическое приложение без зависимостей: простой локальный запуск; компромисс — данные живут в одной вкладке, нет совместной работы и больших объёмов.

### Рост и следующие улучшения

При 100 000 документов нужны серверная обработка очередями, хранилище оригиналов/версий, индекс связей и фактов и постраничная выдача. Права доступа должны проверяться сервером для документа, результата и цитаты; потребуются аудит и изоляция наборов данных. Эти компоненты в MVP не реализованы.

Следующие улучшения по приоритету: (1) расширить размеченный корпус и правила на реальные формулировки; (2) добавить подтверждение неоднозначностей пользователем с журналом решений; (3) добавить версионируемое хранение и права доступа перед многопользовательским пилотом.

### Использование ИИ

Использован Codex: чтение задания, подготовка плана, написание кода, запуск проверок и диагностика. Примеры фактических запросов из этой работы:

- «Подготовь компактный implementation plan» с моделью данных, рисками, этапами и тестами.
- «Реализовать в src/core.mjs: buildContractView(documents, asOfDate) … filterContracts(contracts, { deliveryBefore })».
- «Воспроизведи ошибку автоматическим тестом» для соглашения со словами «Общая стоимость поставки остаётся без изменений».

Реальная ошибка ИИ-кода: наличие цитаты об общей стоимости трактовалось как изменение, поэтому фраза «остаётся без изменений» сбрасывала сумму в `no-data`. Регрессионный тест сначала упал: ожидались 100 000 ₽ и новая поставка 25.03.2026. Исправление отделило упоминание от явного изменения; старую сумму и её источник сохранили. Дополнительный тест проверяет, что явное изменение с нераспознанным новым значением даёт `needs-review`. После исправления тесты проходят. Результаты ИИ проверялись тестами, техническим review и браузерным сценарием; полная переписка не требуется.

### Время и незавершённое

Общий бюджет задания — четыре часа, включая обсуждение, проектирование и README. Суммарные фактические трудозатраты не измерялись таймером, поэтому точное число и соблюдение лимита достоверно подтвердить нельзя. Из журнала известны ориентир начала первой реализации около 23:22 МСК 05.11.2026 и коммит итерации 3 в 00:13 МСК 06.11.2026; это календарные отметки, а не сумма активного времени. Финальная проверка и README выполнены утром 06.11.2026; паузу между сессиями нельзя считать временем разработки.

Обязательная функциональность и документация готовы. Ручная приёмка подтвердила перечисленные выше сценарии, включая изменение суммы в копии, добавление договора и предупреждение о дубликате. Неподтверждёнными остаются ручная проверка изменения срока в копии и остальных предупреждений на нестандартных документах. Пользовательский пилот и предложенные улучшения не выполнялись. Деплой не проводился.
